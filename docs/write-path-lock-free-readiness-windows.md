# 并发写对照复测与无锁化依据（Windows Release）

## 结论

在相同驱动、相同工作负载、按引擎交错顺序复测 5 轮后，本库 8 线程写吞吐中位数为 **40,208 ops/s**，LevelDB 1.23 为 **168,099 ops/s**，RocksDB 11.13.2 为 **394,288 ops/s**。本库并发写分别约为 LevelDB 的 24%、RocksDB 的 10%；并发写采样 p99 为 247 µs，对比 80 µs 和 39 µs。

同一驱动下，本库 8 线程读中位数为 **2,614,064 ops/s**，约为 LevelDB 的 1.62 倍、RocksDB 的 2.26 倍，读路径应继续作为不可退化的能力保护。50/50 单线程混合吞吐为 213,757 ops/s：略高于 RocksDB 的 207,769，但低于 LevelDB 的 316,888。

当前数据**不支持优先做广泛的无锁写入改造**。5 轮诊断中，memtable mutex 获取等待中位数约 1.50 µs/op（计时阶段累计占比约 1.2%）；相比之下，WAL 阶段约 75.4 µs/op（60.5%），immutable 容量等待约 43.2 µs/op（33.3%）。immutable 队列每轮都达到 4 个上限，且出现 slowdown/stop。建议先优化 WAL 排队与 flush/compaction 调度，再用专门的 CAS SkipList 原型验证并发插入的净收益。

## 当前写路径 profile

使用当前 Release `lsm_bench_mt`，启用 `collect_write_path_stats`，8 个线程各 20,000 次并发 Put，5 轮；另有 50/50 并发混合阶段。以下是纯并发写阶段五轮中位数。阶段比例是各写线程累计的已计时耗时比例，不是单线程 CPU 利用率或墙钟时间占比；WAL mutex/队列/I/O 是 WAL 阶段的子项，不得再次加到总阶段上。

| 写阶段 | 中位数耗时 / op | 中位阶段占比 |
|---|---:|---:|
| immutable 容量等待 | 43.2 µs | 33.3% |
| `write_mu_` 获取等待 | 2.07 µs | 1.3% |
| WAL Append 总耗时 | 75.4 µs | 60.5% |
| `memtable_mu_` 获取等待 | 1.50 µs | 1.2% |
| SkipList / memtable Add | 1.96 µs | 1.5% |
| rotate | 2.51 µs | 2.3% |

WAL 细分：队列条件变量等待中位数 **51.5 µs/op**，WAL mutex 获取等待 **10.1 µs/op**，Append I/O 约 **4.0 µs/op**，批次平均 **3.04 条记录**；`sync_wal=false`，Sync 为 0。五轮 immutable 峰值均为 4；slowdown 计数为 230–806，stop 计数为 8–40。后台 flush 记录的平均服务时间中位数约 21.7 ms。

注意当前 flush 诊断的盲区：`BackgroundLoop` 先获取 `flush_mu_`，再启动 flush 计时；`CompactionLoop` 也持有同一个 `flush_mu_` 执行 compaction。因此已有 `background_flush_ns` 不含等待这把锁的时间，不能用其数值排除 flush 被 compaction 延迟。immutable 峰值和写 stop/slowdown 是存在真实背压的证据，但需要补充 `flush_mu_` 等待、immutable 排队时间和 compaction 持锁时长的独立统计来确认因果比例。

## 优化顺序与无锁化决策

1. **先量清楚 flush/compaction 调度并修背压。** 增加 `flush_mu_` 等待时间、每个 immutable 从入队到 flush 完成的延迟、队列水位时间序列、flush/compaction 持锁耗时和 p95/p99 写停顿。之后评估 flush 优先级、compaction 分段让出或后台预算；不能未经正确性设计就让两个线程并行发布 Version/MANIFEST。
2. **再优化 WAL 排队和组提交。** 当前最重的热点是 WAL 总时间与队列等待，而非 memtable mutex。可评估减少 WAL leader/follower 的唤醒与锁临界区、以批次为单位向 memtable 应用、增加显式 WriteBatch 以摊薄每次调用开销。不要简单增加固定等待来攒批；历史试验中人为延迟降低吞吐并恶化尾延迟。写成功仍必须遵循 WAL 顺序/错误语义。
3. **最后做受控的无锁 memtable 插入原型。** 现有 SkipList 的 next 指针已是 atomic，读路径已经无锁；但 `Insert` 用 store 而不是 CAS，前驱搜索、随机高度 RNG、Arena 分配和多层链接均依赖 `memtable_mu_` 串行化。若做实验，保留 memtable rotate/freeze 门闩与 WAL 序号协议，先 CAS 发布 level 0，再逐层发布上层链接；采用线程安全的 RNG 和并发安全 Arena 分配。SuperVersion 的 `shared_ptr` 生命周期可支持旧 memtable 在读者退出前保留，但仍需证明发布顺序、层级搜索正确性、size/bytes 阈值精确性及并发 flush 边界。
4. **采用 A/B 和完整验收，而不是以“无锁”本身为目标。** 同一交错五轮基准要求 8 线程写吞吐显著超过当前 40,208 ops/s、p95/p99 不劣于当前 135/247 µs；8 线程读至少保持当前 2,614,064 ops/s（复测噪声范围内），且单线程读写/混合不退化。每个候选必须通过同 key 并发、WAL 失败/重启、immutable 背压、重复随机模型、Release 回归和可用的并发内存检查。若消除 `memtable_mu_` 等待仍只带来噪声级变化，应撤销原型，转回 WAL 和调度优化。

当前实际证据意味着“锁自由改造”应是后续可证伪实验，而不是下一步直接重写 Put/Get：粗略地，互斥量等待只占测得阶段约 1.2%，远低于容量等待和 WAL 排队；而 Get 已经无锁且领先竞品。下一轮优先给 WAL 和 flush/compaction 补齐可解释的等待分解，完成调度/组提交 A/B 后，再判断 lock-free SkipList 的收益上限是否值得其复杂度。
